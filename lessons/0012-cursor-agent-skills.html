Lesson 12 · ~20 minutes

Cursor Agent Skills

Rules tell Agent how to behave always. Skills teach Agent how to run a workflow once.

In Lesson 3 you wrote project rules — short prose loaded every session. In Lesson 11 you added hooks — scripts that fire on agent events. Skills sit between them: reusable multi-step procedures Agent loads only when relevant, keeping your context window lean.

Think of a skill as a playbook you write once and invoke many times: ship the habit tracker, review a PR your way, run a security audit. Same idea as the verify loop from Lesson 4, but packaged so Agent follows it without you re-pasting the checklist. Keep the Skills reference open.

Four layers, one stack

LayerMechanismExample
Rules Prose in .cursor/rules/ "Use TypeScript + Drizzle"
Skills SKILL.md workflows "Run verify loop before ship"
MCP External tools Playwright opens localhost
Hooks Event scripts Log every shell command

They complement each other. Your habit tracker might have a rule for stack choice, a ship skill for the verify checklist, Playwright MCP for browser checks, and an audit hook you installed in Lesson 11.

Rules vs skills — the split

Project rulesAgent skills
Always loaded — small, stable prefs Loaded on demand — longer procedures
"Prefer npm test over manual curl" Step-by-step: run test → e2e → report
Good for conventions Good for workflows you run sometimes
Don't duplicate
If a preference applies every session, keep it in rules. If it's a multi-step checklist you run when finishing a feature, make it a skill. Duplicating the same text in both wastes context.

How skills load (progressive disclosure)

Discovery At startup, Agent sees every skill's name and description — lightweight metadata only
Activation When your prompt matches the description — or you type /skill-name — the full SKILL.md loads
On demand During execution, Agent reads linked reference.md files or runs scripts/ only if needed

This keeps long workflows out of context until you need them. Official docs: Cursor — Agent Skills.

Two config locations

Project .cursor/skills/your-skill/SKILL.md — commit to git; shared with anyone cloning the repo
Personal ~/.cursor/skills/your-skill/SKILL.md — available in every workspace on your machine

Cursor also discovers .agents/skills/ (this teaching workspace uses that path for the teach skill). Prefer .cursor/skills/ for new project skills — it's the canonical path in current docs.

SKILL.md structure

Each skill is a folder with a required SKILL.md. YAML frontmatter at the top; markdown body with instructions below. 

---
name: habit-tracker-ship
description: Run the habit tracker verify loop after a feature change. Use when shipping, verifying, or finishing work on the habit tracker API or UI.
---

# Habit Tracker Ship

## Verify checklist
- [ ] npm test — all API tests green
- [ ] npm run test:e2e — browser happy path (add, toggle, delete)

## Done when
All checks pass. If something fails, show the command output and fix before marking done.

Skip manual browser smoke here — your Playwright e2e suite already covers the same happy path with explicit assertions. E2e is deterministic; ad-hoc clicking depends on whatever the model decides to test. See the UI Verify reference — once e2e is stable, it replaces the manual Run step from Lesson 7. Keep manual clicking for new UI slices (layout, feel) while building — not as a gate on every ship.

Two fields are required. name must match the folder name (lowercase, hyphens). description is the most important line — Agent uses it to decide when to auto-apply the skill. Write the words you would actually type: "ship", "verify", "finish", "check before merge."

Optional frontmatter

FieldEffect
paths Glob patterns — skill only surfaces when Agent works on matching files (e.g. src/api/**)
disable-model-invocation: true Slash-command only — Agent won't auto-apply; you must type /skill-name

Start without disable-model-invocation so Agent can discover your ship skill when you say "verify the habit tracker." Add slash-only mode later for destructive or billing-sensitive workflows.

Three ways to invoke

MethodWhen to use
/habit-tracker-ship Explicit — you know exactly which playbook to run
@ attach the skill Pin it to one message without typing the slash command
Natural prompt "Verify the habit tracker before I commit" — Agent matches description

Cursor also ships a built-in authoring skill: type /create-skill in chat and describe what you want. Use it when you're unsure of structure; use manual authoring when you know exactly what the workflow should be.

Starter skill: habit-tracker-ship

Your habit tracker already has API tests, Playwright e2e, and a shell audit hook. Codify the verify loop from Verify Loop reference as a project skill — so every "done" session runs the same checks: unit tests plus e2e, not a redundant manual smoke pass. 

mkdir -p .cursor/skills/habit-tracker-ship
# Create .cursor/skills/habit-tracker-ship/SKILL.md (template above)
# Commit the skill folder — no secrets, no .env paths

Optional: add scripts/run-verify.sh inside the skill folder if you want one command Agent can execute instead of re-typing steps. Keep SKILL.md concise; put long detail in a linked reference.md.

Five-step authoring loop

1. Pick one workflow One skill = one procedure. Not "everything about this repo."
2. Write description first Include trigger words users type — this drives discovery
3. Create folder + SKILL.md .cursor/skills/name/SKILL.md — name matches folder
4. Test invocation Type /name or prompt naturally; confirm Agent follows steps
5. Commit Project skills belong in git — they're team (or future-you) documentation
Description is the trigger
If your skill never fires, the description is too narrow. Add synonyms: "verify", "check", "ship", "done", "before commit." Not "handles quality assurance procedures."

Check your understanding

1. Share skills via git with team.

2. Agent loads skill on demand.

3. Force invoke a skill manually.

Do this now

Create one project skill on your habit tracker — codify the verify loop you already use.

  1. Create .cursor/skills/habit-tracker-ship/SKILL.md using the template above — adjust commands to match your repo (test script name, e2e command).
  2. Write the description with words you'd actually say: "verify habit tracker", "ship", "check before commit."
  3. Invoke — type /habit-tracker-ship or ask Agent to "verify the habit tracker is ready to ship."
  4. Confirm Agent runs your checklist (npm test, npm run test:e2e) and reports pass/fail.
  5. Commit the skill folder to git.

You are done when Agent follows your skill's checklist on a real invocation without you re-pasting the steps.
