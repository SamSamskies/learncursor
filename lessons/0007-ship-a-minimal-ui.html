Lesson 7 · ~15 minutes

Ship a Minimal UI Slice

Green tests prove the API works. A working first version is something you can click.

In Lesson 6 you shipped the completion toggle — schema, route, tests, all green. Your habit-tracker backend is done. But your mission success criterion is a working first version, not a test suite you admire from the terminal.

A UI slice is the smallest clickable surface that exercises your API: list habits, add one, toggle today, delete one. No auth, no design polish, no mobile breakpoints — just proof the app works end to end.

Why this is Plan Mode again

Slice touches…Reach for…
One new route mirroring an existing handler Agent + @ — Lesson 5
Page + static serve + fetch client + server tweak Plan Mode → Build — reference
Wrong button color after build Inline Edit (Cmd+K) on those lines

A UI slice typically spans four concerns at once: where files live, how the server serves them, how the page calls /api/*, and whether existing tests still pass. That is multi-file work — plan first, same workflow as Lesson 6.

Extend your done-when

Lessons 4–6 stopped at npm test. For UI work, add a fourth check — the Run step. Keep the UI Verify reference open.

Scope Only UI wiring — no API redesign, no new tables.
Patterns Matches your TypeScript + Drizzle project rule.
Tests npm test — run it yourself.
Run npm run dev → browser smoke test (add, toggle, reload, delete).
Browser beats description
"It should work" is not verification. Click through the happy path yourself. Reload the page — does toggle state persist? That is your real done-when.

Sample plan prompt

Goal: Minimal UI — list habits, add habit, toggle today's completion, delete habit.
Scope: Single page served from existing server. Fetch existing /api routes only. Plain CSS OK.
Constraints: Match project stack (TypeScript). No auth, routing library, or component framework unless already in repo.
Done-when: npm test green; npm run dev; browser — add habit, toggle, reload persists, delete works.

Review the plan for: which URL serves the page, where static files live, how fetch errors surface (even a simple alert is fine for v1), and whether the server needs a one-line static middleware change. Edit until those are explicit — vague plans produce pages that 404.

Pro workflow (same as Lesson 6)
Plan with Opus or GPT-5.x locked → review plan → Build with Composer or Auto → four-step verify. Small DOM or CSS fixes afterward: Inline Edit, not a new plan.

Check your understanding

1. All tests green, nothing to click. First version done?

2. UI needs page, client, and server change.

3. Browser works but npm test fails.

Do this now

20-minute win in your habit-tracker repo.

  1. Open Plan Mode (Shift+Tab). Lock Opus or GPT-5.x.
  2. Paste the UI prompt above — adjust if your server already serves static files.
  3. Review the plan — confirm file paths, serve URL, and all four done-when checks.
  4. Build with Composer or Auto.
  5. Four-step verify — scope, patterns, npm test, then browser smoke test per the UI Verify reference.

You are done when you can demo add → toggle → reload → delete in the browser and tests stay green.
