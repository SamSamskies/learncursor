Lesson 15 · ~20 minutes

PR Review Agents

Lesson 9 taught you to respond to review comments. This lesson teaches you to catch issues before they become comments.

In Lesson 9 you fixed CodeRabbit feedback on your bitcoin-connect PR. In Lesson 14 you configured cloud verify for habit tracker. Now Cursor's own review stack closes the loop: Bugbot (general PR review), Security Agents (vulnerability-focused), and Approval Agents (team auto-approve gate). Keep the PR Review Agents reference open.

One lesson, three layers — on purpose.
Approval Agents explicitly consume Bugbot and Security findings. Teaching them together shows the full pipeline. For your solo workflow, Bugbot + local /review are the actionable parts; Security and Approval matter when you join a team or harden your own repos.

The pipeline

On PR Bugbot Bugs, quality, fix suggestions on GitHub

Layer 1 — Bugbot

Bugbot reviews pull request diffs and leaves inline comments with explanations and fix suggestions. You already have GitHub connected through the dashboard (from Lesson 10) — that same integration powers Bugbot on your PRs.

On GitHub

  • Runs automatically on each PR update (unless you set mention-only)
  • Manual trigger: comment cursor review or bugbot run
  • Reads existing PR comments — avoids duplicating CodeRabbit-style feedback
  • Publishes a Cursor Bugbot check — success when clean; findings default to neutral
  • Fix in Cursor / Fix in Web links jump you into an agent with context

Before you push — /review-bugbot

Cursor 3.7+ ships review skills in the IDE. Type /review-bugbot (or /review to pick agents) in Agent chat. By default it reviews branch changes — everything since the merge-base with your default branch, including uncommitted edits.

Patch ID sync — the killer feature for solo builders.
When you run /review-bugbot locally, then open a PR with the same diff, Bugbot on GitHub recognizes it already reviewed that patch and skips the remote run — leaving a comment that says so. Fewer duplicate bot comments, faster merge.

Project rules for Bugbot — BUGBOT.md

Like project rules for Agent, Bugbot reads .cursor/BUGBOT.md files. The root file always applies; nested files apply when reviewing changes under that path. Use them for repo-specific expectations — e.g. "flag missing tests when server/ changes."

Bugbot Autofix (optional)

When Bugbot finds issues on a PR, Autofix can spawn a cloud agent to fix them and push to a new branch (recommended) or the same branch. Requires on-demand billing. Solo pattern: start with Autofix off; use Fix in Cursor when you want to stay in control.

Layer 2 — Security Agents

Bugbot catches general bugs and some security issues. Security Agents are dedicated — prompt-tuned for vulnerabilities, with checks you can enable or disable per agent. Cursor built them because a general reviewer cannot block CI on security-only findings without blocking every style nit. Blog: securing with autonomous agents.

Two agent types

TypeTriggerBest for
Security Reviewer PR opened / updated (Automations) Catch vulns in incoming changes
Vulnerability Scanner Cron (Automations) Find pre-existing issues in the whole repo

Both run on the Automations platform (cloud agents). Configure from the Security Agents dashboard — same trigger model you learned in Lesson 13.

Before you push — /review-security

Same diff scope as Bugbot: branch changes vs base by default. Run both before a sensitive change (auth, payments, user data). Type /review to run either or both in one flow.

Solo vs team

/review-security in the IDE works on individual plans. Scheduled Security Reviewer / Scanner automations bill to the team usage pool. For habit tracker or personal repos, local pre-push review is enough unless you want weekly cron scans — then treat it like your verify automation.

Layer 3 — Approval Agents

Approval Agents sit on top of PRs. They auto-approve when your criteria are met, or assign reviewers when more eyes are needed. They do not replace thoughtful human review — they automate the boring "LGTM on a typo fix" cases on teams with many PRs.

How they use Bugbot and Security

In the Approval Agents dashboard, enable review signals:

  • Bugbot Review Context — waits for Bugbot, reads findings
  • Security Review Context — waits for Security Agents (team plan)
  • Risk Score — classifies PR risk; set max threshold for auto-approve

If Bugbot or Security report findings that need human review, the Approval Agent will not auto-approve — even if the diff looks small. When policies conflict, the stricter instruction wins.

Policy files in the repo

FilePurpose
APPROVAL_POLICY.md Per-directory rules — closest ancestor wins
.cursor/approval-policies/ROUTING.md Top-level routing by product / path boundary

Safety guard: if a PR edits approval policy files themselves, the agent uses the base-branch version and defaults to human review — so nobody sneaks relaxed rules through in the same PR.

What solo builders do instead

Approval Agents are a team feature. Your equivalent workflow:

  1. Run /review locally before push
  2. Open PR — read Bugbot (and maintainer) comments
  3. Fix with the Lesson 9 loop — one commit per concern
  4. Merge when checks are green and you trust the diff

You already did steps 2–4 on bitcoin-connect. Adding step 1 catches Bugbot-class issues before CodeRabbit or maintainers see them.

Local vs GitHub vs team — quick map

Do not confuse PR review agents with your habit tracker verify automation. Verify runs tests on a schedule. Bugbot reviews code diffs on PRs. Different triggers, different outputs — both belong in a mature repo.

Do this now

Run a pre-push review on habit tracker or a small branch

  1. Pick a repo — habit tracker with uncommitted changes, or a feature branch with a few commits. Make sure you are on the branch you would PR.
  2. Run /review-bugbot in Agent — read the findings table (Severity, Location, Finding). Fix anything valid before push.
  3. Optional: /review-security — if your diff touches auth, API routes, or user input, run security review on the same diff.
  4. Enable Bugbot — Cursor dashboard → Bugbot → confirm habit tracker (or your OSS fork) is enabled. Note personal settings: mention-only vs auto, incremental review.
  5. Optional: .cursor/BUGBOT.md — one rule for habit tracker, e.g. "require test changes when src/routes/ changes." Commit and push.
  6. Open or update a PR — if you ran local review first, watch for Bugbot's skip comment on GitHub. Triage any new findings with the Lesson 9 loop.

You are done when you have run at least one local /review-bugbot, know where Bugbot is enabled in the dashboard, and can explain what Approval Agents add that you handle manually as a solo builder.
