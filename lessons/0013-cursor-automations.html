Lesson 13 · ~20 minutes

Cursor Automations

Skills run when you ask. Automations run when the world changes — or the clock does.

In Lesson 12 you packaged the habit tracker verify loop as habit-tracker-ship — a skill Agent loads when you are at the keyboard. In Lesson 11 you added hooks that fire on local agent events. Automations are the cloud layer: a cloud agent that wakes up on a schedule or an external event and does work while you are away.

For a solo builder, that closes the loop. You ship a slice locally, verify with your skill, commit — and an automation can re-run that verify every week, review PRs on your OSS repo, or triage Slack messages without you opening the IDE. Keep the Automations reference open.

Local stack vs cloud automations

SurfaceRuns whereYou start it
Agent + skills Your machine Yes — chat prompt or /skill-name
Hooks Your machine No — fires on agent events
Automations Cursor cloud No — trigger fires (cron, PR, Slack, …)

Think of it as when you're there vs when you're not. Rules, skills, and hooks optimize your active sessions. Automations handle maintenance, review, and triage on their own schedule.

What an automation is made of

Trigger When to run — cron schedule, PR opened, Slack message, webhook POST, Linear issue, Sentry error, …
Tools What the cloud agent may use — comment on PR, send to Slack, MCP servers, memories, computer use
Prompt Instructions — same spirit as a cloud agent chat, but written once
Repo scope None, single repo, or multi-repo — where the agent checks out code

Official docs: Cursor — Automations. Automations always run as cloud agents in Max Mode and bill to your usage pool.

Dashboard GitHub — required for PR triggers

You connected GitHub in the Cursor dashboard in Lesson 10. That integration powers cloud agents, Bugbot, and automations — it is not the same as GitHub MCP in your local project. PR-triggered automations need the dashboard connection; local Agent can still use gh or GitHub MCP when you are in the IDE.

Private automations open PRs as you
Comments and review actions appear as cursor. Slack messages come from the Cursor bot. Plan permissions accordingly on shared repos.

Triggers that fit a solo builder

TriggerExample use
Schedule (cron) Weekly npm test + e2e on habit tracker
PR opened / pushed First-pass review on your app repo or OSS target
PR commented Draft a response to review feedback overnight
Webhook Your CI or monitoring POSTs to start a run
Slack message Triage bugs posted to a public channel

Cron and Slack triggers default to no repository. If the automation should run tests or edit code, explicitly attach your habit tracker repo and branch in settings.

Skills meet automations

Your committed habit-tracker-ship skill lives in the repo. When a cloud agent checks out that repo, it can discover and follow the same verify checklist you use locally. Reference it by name in the automation prompt — you do not need to re-paste the full steps. 

When this automation runs on the habit tracker repo:

1. Follow the habit-tracker-ship skill verify checklist.
2. Run npm test and npm run test:e2e.
3. If all pass: post a one-line summary (or write a memory note — your choice).
4. If any fail: summarize failing commands and output. Do not open a PR.

Skills = local playbook on demand. Automations = cloud playbook on a trigger. Same workflow, different runtime.

Three ways to create one

PathBest for
Agents Window + /automate Describe what you want in plain language; Agent drafts trigger, tools, prompt
cursor.com/automations Visual editor, templates, managing existing automations
Cursor Marketplace templates Starting points — PR review, failed CI triage, Sentry investigate

The /automate skill walks through trigger → tools → prompt → name, then opens the Automations editor with a draft you review and save. Use the Agents Window for that path — it needs the in-app Automations handoff.

Starter automation: weekly habit tracker verify

A low-risk first automation for your mission: no PR comments, no code changes — just confirm the app still passes tests while you are away.

SettingValue
NameHabit tracker weekly verify
TriggerSchedule — once per week (pick a quiet time)
RepoSingle — your habit tracker, default branch
ToolsBase cloud agent only (terminal/git). Skip Slack unless you want alerts.
PermissionsPrivate — bills to you, only you manage it

Stretch goal after the first one works: a PR opened automation on an OSS repo you contribute to — same review instincts from Lesson 9, running in the cloud.

Do this now

Create your first automation — weekly habit tracker verify

  1. Open the Agents Window — automations are created and managed there or at cursor.com/automations.
  2. Start with /automate — say: "Weekly automation on my habit tracker repo. Run npm test and npm run test:e2e using the habit-tracker-ship skill. Report pass or fail. Do not open a PR."
  3. Review the draft — confirm trigger (weekly cron), single repo + branch, and prompt match the table above.
  4. Save and activate — finish any picker fields the editor still needs (schedule time, repo).
  5. Confirm a run — trigger manually if the editor offers it, or wait for the first scheduled run and check the run log.

You are done when one automation run completes and reports test results for your habit tracker.
