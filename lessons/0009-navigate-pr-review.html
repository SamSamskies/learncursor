Lesson 9 · ~15 minutes

Navigate PR Review

Opening the PR is half the job. Landing it means reading feedback, changing little, and proving it still works.

In Lesson 8 you opened PR #395 on bitcoin-connect — a focus trap for keyboard users in the payment modal. CodeRabbit left two actionable comments. This lesson is about turning those into clean follow-up commits without scope creep.

Review is not rejection

Maintainers and bots comment to help you merge, not to block you. A typical first PR gets 1–5 rounds of small fixes. That's normal. Your job:

  • Read every comment — human and bot
  • Decide: fix, push back, or ask — most comments deserve a fix
  • One commit per logical fix — easier to review than a squashed mess
  • Re-run their verify command — same done-when as Lesson 8

Four-step review loop

1. Paste Copy review comments (or the PR URL) into Agent. Ask which are valid and what files to touch.
2. Scope One prompt per comment — even in the same file. No "while we're here" refactors.
3. Verify Run the same local test you used before (yarn dev + keyboard check).
4. Reply Push commit(s). Reply on GitHub: "Fixed in abc123" or explain why you disagreed.

Sample fix prompts

Your two comments are in the same file but are separate concerns — markup vs lifecycle. Fix them with two prompts and two commits, not one batched prompt. Combine only when comments are tightly coupled (e.g. a bug fix and its test).

Prompt 1 — accessible name

PR review on @src/components/bc-modal.ts — one change only:
Add an accessible name to the dialog (aria-label or aria-labelledby).
No other changes.

Prompt 2 — inert restore (after reviewing the diff from prompt 1)

PR review on @src/components/bc-modal.ts — one change only:
On mount, save each body sibling's current inert value in a Map;
on unmount restore those exact values instead of setting all to false.
No other changes.

Run yarn dev and keyboard-check the modal after each prompt, or once at the end if both diffs are small and you read them line by line.

When to push back

You are allowed to disagree — politely and with evidence. Good reasons:

  • The comment is out of scope for the linked issue
  • The suggested fix breaks an existing pattern in the repo
  • You verified the concern doesn't reproduce locally

Bad reason: "the bot is annoying." If a human maintainer repeats the bot's point, treat it as required.
