Lesson 10 · ~20 minutes

Integrate MCP Into a Project

@ mentions give the agent your files. MCP gives it your tools — GitHub, browser, database, APIs.

In Lesson 5 you learned to point Agent at code with @. That context lives inside your repo. Model Context Protocol (MCP) extends Agent with external capabilities: query GitHub, drive a browser, read a database schema, call a docs API — without you copy-pasting into chat.

This lesson is about the project-level pattern: a .cursor/mcp.json file you commit so every session in that repo gets the same tools. Same idea as project rules, but for live integrations. Keep the MCP Setup reference open.

What MCP changes

Without MCPWith MCP
Paste PR comments into chat Agent reads the PR via GitHub tools
Describe "Tab doesn't reach Confirm Payment" Browser MCP opens the modal and checks focus
Copy schema from a dashboard Database MCP lists tables and columns

Agent decides when to call MCP tools — you prompt the goal, it picks the tool. You still read diffs and verify results; MCP removes the fetch-and-paste grunt work.

Two config locations

Global ~/.cursor/mcp.json — personal tools in every workspace (your GitHub token, personal Notion, etc.)
Project .cursor/mcp.json in repo root — shared with the team via git; project config wins on name conflicts

Solo builders often start global, then move repeatable setups into the project file once a stack stabilizes — exactly like user rules → project rules in Lesson 3.

Project config shape

Most MCP servers are stdio — Cursor spawns a local process. Remote servers use a url instead. Official docs: Cursor — MCP. 

// .cursor/mcp.json  (commit this file)
{
  "mcpServers": {
    "github": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": {
        "GITHUB_PERSONAL_ACCESS_TOKEN": "${env:GITHUB_PERSONAL_ACCESS_TOKEN}"
      }
    }
  }
}

${env:VAR} reads from your shell or .env — never hardcode tokens in json you commit. Add .env to .gitignore if it isn't already.

Pick a server for your project

You're working on…Start withExample prompt after setup

App with UI (habit tracker) Playwright / browser MCP Open localhost:3000 and confirm toggle works
App with Supabase / Postgres Supabase or Postgres MCP Show columns on the habits table
Install only what you need
Each MCP server exposes tools Agent can invoke. More servers = more attack surface and context noise. One well-chosen server beats five "just in case" installs. Prefer official or widely audited packages.

Five-step setup loop

1. Create mkdir -p .cursor → add mcp.json with one server entry
2. Secret Export token in shell or .env; reference via ${env:…}
3. Reload Command Palette → Developer: Reload Window (MCP loads at startup)
4. Confirm Settings → Tools & MCP — server shows connected (green)
5. Prompt Ask Agent something only that tool can answer; watch it call the tool

Sample project rule (optional)

MCP tells Agent what tools exist. A one-line project rule tells it when to prefer them — add to .cursor/rules/ if you want consistency: 

When I mention a GitHub PR or issue by number, use the GitHub MCP
tools to fetch details instead of asking me to paste them.

Check your understanding

1. Team shares MCP via git.

2. API token in mcp.json.

3. Just edited mcp.json.

Do this now

Wire one MCP server into a real project — pick the row that matches what you're building.

  1. Choose a project — habit tracker, bitcoin-connect, or your next app idea.
  2. Create .cursor/mcp.json — one server from the table above; use ${env:…} for secrets.
  3. Set the secret — export in terminal or add to local .env (not committed).
  4. Reload Window — confirm green in Settings → Tools & MCP.
  5. Test prompt — ask Agent something only that MCP can answer; confirm you see a tool call in the trace.
  6. Commit — mcp.json only (no secrets). Optional: add the one-line project rule.

You are done when Agent successfully calls the MCP tool once on a real task.
