Plan Mode for Bigger Slices

Agent plus @ mentions wins on single routes. Schema plus routes plus tests is a plan-first job.

In Lesson 5 you shipped GET and DELETE /api/habits with thin prompts and @ context. That pattern stops scaling when a feature spans several layers — new Drizzle table, migration, route, and tests all at once.

Plan Mode researches your repo, asks clarifying questions, and writes a reviewable plan before any code lands. You edit the plan, then click Build. (Mission: reach a working first version in one focused session — planning is how you keep that session from becoming a refactor spiral.)

When to escalate

You are doing…Reach for…
Mirror an existing route (GET like POST) Agent + @ files — Lesson 5
New table + API + tests in one slice Plan Mode → Build
New app idea, stack not chosen Plan Mode with a frontier model

Keep the Plan Mode reference open while you work.

How Plan Mode works

Prompt Same anatomy as Agent: Goal, Scope, Done-when. Agent explores the codebase.
Answer Reply to clarifying questions — default date timezone? Row insert/delete or boolean flip?
Review Edit the plan: which files, migration order, test cases. Save to workspace if useful.
Build Click Build. Switch to Composer or Auto — check the model didn't reset to Auto mid-flow.
Verify Run the verify loop on the full diff, not just tests.

Open Plan Mode with Shift+Tab in the Agent input.

Pro tip (Cursor Pro)
Lock Opus or GPT-5.x for planning and refinement. Switch to Composer 2.5 or Auto when you click Build — save the API pool for decisions, burn the cheaper pool on implementation.

Sample plan prompt

Your habit API is in place. A natural next slice is completions — marking a habit done (or undone) for a given day:

Goal: Add completion toggle — POST /api/habits/:id/toggle flips done state for a date.
Scope: Drizzle schema + migration, route handler, tests only. No UI yet.
Constraints: Optional { date } in body, defaults to today (UTC). No row = insert; row exists = delete.
Response: { habitId, date, completed } reflecting new state. 404 if habit missing.
Done-when: npm test — all green.

Plan Mode should propose: a completions table with a unique (habit_id, date) constraint, migration steps, the route, and test cases for toggle on, toggle off, default date, and missing habit. You review and edit that list before Build touches your repo — swapping check-ins for toggle, picking UTC vs local, or tightening the response shape is normal plan work.

Review checklist
Before Build, confirm the plan names: toggle semantics (insert/delete vs boolean flip), date format and default, response body, and at least five test cases. Vague plans produce vague diffs.

When the build goes wrong

Don't steer a bad multi-file diff with ten follow-up prompts. Official guidance: revert, make the plan more specific, build again. The plan is cheaper to edit than the code.

Check your understanding

1. Toggle needs schema, route, and tests. Best surface?

2. Build shipped wrong toggle logic. Best recovery?

3. Brand-new app idea, stack not chosen. First move?

Do this now

15-minute win in your habit-tracker repo.

  1. Open Plan Mode (Shift+Tab). Lock Opus or GPT-5.x for planning.
  2. Paste the toggle prompt above — or your own wording if you already started a plan.
  3. Review the plan — use the checklist above; edit endpoint shape, date handling, or tests until nothing is vague.
  4. Build with Composer or Auto. Run the verify loop: scope → patterns → npm test.

You're done once toggle passes all three verify checks and tests are green.
