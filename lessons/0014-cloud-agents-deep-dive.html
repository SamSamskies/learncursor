Cloud Agents Deep Dive

Automations are one way to start a cloud agent. This lesson is about what actually runs when they do.

In Lesson 13 you created a weekly verify automation — a cloud agent that wakes on a cron trigger. You know that it runs in the cloud. This lesson covers how: the VM, the dev environment, run logs, when to use cloud vs local, and how to debug when a run fails. Keep the Cloud Agents reference open.

Same agent, different machine

Cloud agents use the same agent fundamentals as local Agent — tool calls, terminal, file edits, follow-up messages — but they run in an isolated Ubuntu VM in Cursor's cloud, not on your laptop. They clone your repo from GitHub, run in Max Mode, and bill to your usage pool.

Local AgentCloud Agent
Checkout Your working tree Fresh clone at trigger time
Hooks Your hooks.json runs Not available
Local MCP Playwright, project mcp.json Dashboard MCP only
Skills Auto-discovered from repo Same — if committed and pushed
You intervene Chat in IDE Agents Window, web, or follow-up on run

Every way to start one

Your weekly automation is one entry point. Cloud agents also start from:

SurfaceHow
Agents Window Cmd+Shift+P → Open Agents Window — unified view of all runs
Web cursor.com/agents — start, monitor, intervene from any device
IDE dropdown Select Cloud under the agent input (not Local)
Automations Cron, PR opened, Slack, webhook — trigger → run
GitHub Comment @cursor on a PR or issue (dashboard GitHub required)
CLI handoff Prepend & to a message to push work to cloud
Agents Window is the control plane.
A run started from your automation, from the web, or from GitHub all appear in the same place. Status (running, waiting, done), transcript, and environment details live there — not buried in email.

What happens during a run

1. Boot VM Cursor starts an isolated machine and selects the dev environment for your repo
2. Install Runs the install command — usually npm install — to sync dependencies
3. Agent loop Reads prompt, discovers committed skills, runs terminal commands, may open a PR
4. Outcome Summary in run log, PR, PR comment, Slack message, or memory note — depending on tools enabled

On the run page, hover the repository name at the top to see which environment was used. That is the first thing to check when a verify automation fails at install or test time.

The dev environment — the part that matters most

Cursor's docs are blunt: not giving cloud agents a dev environment is like not giving engineers a computer. An agent that can edit code but cannot install deps or run tests cannot close the loop.

For your habit tracker weekly verify, the cloud agent needs:

  • Node + npm available in the VM
  • npm install succeeding on clone
  • Playwright browsers installed if e2e runs headless in cloud (may need extra setup)
  • Committed habit-tracker-ship skill in the repo branch the automation checks out

Resolution order when a run starts: repo environment.json → personal saved environment → team saved environment. Full details: Cloud agent setup. 

// .cursor/environment.json — minimal starter for Node repos
{
  "install": "npm install"
}

The install command must be idempotent — it may run on partially cached state. After a slow install, Cursor checkpoints the VM so future runs start faster.

Secrets go in the dashboard, not git.
API keys and test credentials belong in Cursor dashboard → Cloud Agents → Secrets. Cloud agents read them as environment variables. Do not commit .env files for cloud use.

AGENTS.md for cloud-only instructions

Cloud agents read AGENTS.md. Add a section like ## Cursor Cloud specific instructions for steps that differ from local dev — e.g. "e2e runs headless with npm run test:e2e; no dev server needed if tests start their own server."

This complements your skill: the skill is the verify checklist; AGENTS.md is environment context the agent needs before it can run that checklist in a VM.

Local MCP ≠ cloud MCP

You installed Playwright MCP locally in Lesson 10. That config does not automatically transfer to cloud agents. Cloud agents use MCP servers configured in the dashboard MCP dropdown at cursor.com/agents — HTTP transport recommended; credentials are proxied, not exposed in the VM.

NeedLocalCloud
Browser verify in IDE Playwright MCP in project Computer use (VM desktop) or terminal e2e
Open PR while away Not without you Dashboard GitHub integration
Database queries Project or global MCP Dashboard MCP (must be connected + authed)

When to use cloud vs local

Stay localSend to cloud
Active iteration — you are reading diffs live Weekly verify while you are away (your automation)
Hooks gating shell commands Multi-hour refactor — start and walk away

Plan Mode architecture decisions Hand off from CLI with & mid-session

Solo-builder pattern: build and verify locally, then automate or cloud-handoff for maintenance and review. Your habit tracker stack already follows this.

Reading a run log

When your weekly automation completes (or fails), open the run in cursor.com/agents or the Agents Window. Read top to bottom:

  1. Environment — which snapshot or config; any warning banner?
  2. Install step — did dependency setup finish?
  3. Agent transcript — which commands ran; did it find your skill?
  4. Outcome — pass/fail summary, PR link, or error

Common failures for verify automations:

  • Repo not pushed — cloud clones remote, not your laptop
  • No environment — install never ran or wrong Node version
  • E2e needs browsers — Playwright install step missing from environment
  • Snapshot expired — warning banner; re-run setup or restore version

You can intervene mid-run: send a follow-up message in the run thread, or take remote desktop control to inspect the VM, then hand back to the agent. See Capabilities for computer use and artifacts on PRs.

Automations revisited

An automation is a cloud agent with a saved prompt, trigger, and optional tools (PR comment, Slack, memories). Everything in this lesson applies to your weekly verify — you are already operating cloud agents; this lesson gives you the dashboard literacy to trust and debug them.

Memories (optional automation tool) let an agent write notes across runs — useful for triage agents, less so for a pure test verify. Enabled by default; disable if the automation handles untrusted input.

Do this now

Inspect and improve your habit tracker cloud setup

  1. Open the control plane — go to cursor.com/agents or the Agents Window. Find your weekly verify automation's latest run (or trigger a manual run from the automation editor).
  2. Read the run log — note environment name, install step result, commands the agent ran, and pass/fail outcome. Paste anything unclear to your agent teacher.
  3. Check the environment — Cloud Agents dashboard → Environments. Does your habit tracker repo have one? If not, start agent-driven setup or add .cursor/environment.json with "install": "npm install" (plus Playwright browser install if e2e needs it).
  4. Add cloud hints — in your habit tracker repo, add a ## Cursor Cloud specific instructions section to AGENTS.md: how to run tests headless, any secrets the cloud VM needs from the dashboard.
  5. Re-run — trigger the automation manually or kick off a one-off cloud agent: "Follow habit-tracker-ship. Run npm test and npm run test:e2e. Report pass or fail. Do not open a PR."

You are done when you can explain what happened in a cloud run (environment → install → tests → outcome) and your verify passes or you know exactly why it failed.
