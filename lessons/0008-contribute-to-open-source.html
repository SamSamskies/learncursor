Contribute to Open Source

You built a habit tracker from nothing. Now prove the workflow works on code you didn't write.

In Lesson 7 you reached a working first version — UI, API, tests, and (bonus) Playwright e2e. That completes the solo-builder arc in your mission. One success criterion remains: clone an unfamiliar repo and make a meaningful contribution using Agent.

OSS is different from your habit tracker. You don't set the rules, the folder layout, or the test command. The skill is not "write perfect code" — it's learn fast, change little, verify with their toolchain. Keep the OSS Workflow reference open.

Explore before you @
On your repo, @ mentions save time because you already know what's relevant. On a foreign repo, premature @ files can mislead Agent. Start with open questions — let Agent search. See the prompting docs: "If you're not sure which files matter, skip it — Agent finds relevant files through its own search."

Pick the right first issue

Your first OSS contribution should be boring on purpose. Look for:

  • Small scope — typo, missing validation, broken link, test gap
  • Stack you recognize — TypeScript, Python, whatever you know
  • Active repo — merged PRs in the last month; responsive maintainers
  • Clear repro — issue describes expected vs actual behavior

Avoid "good first issue" labels on abandoned repos, and avoid issues that say "refactor the entire module." One file changed is a win.

Five-phase workflow

1. Pick One issue. Read it fully. Check if a PR already exists.
2. Clone Fork if needed. git clone → open folder in Cursor.
3. Explore Paste the issue link into Agent and ask where to look. Run their install + test commands yourself.
4. Change Agent + @ on the 1–3 files you identified. Tight scope in the prompt.
5. Verify Their test/lint command green. Review diff for unrelated changes. Open PR linking the issue.

Sample explore prompt

Paste the full issue URL and copy the title plus a sentence or two from the description — Agent may not fetch GitHub links on its own, but the URL anchors the task for you. 

I want to fix: https://github.com/owner/repo/issues/42
Title: [paste issue title]
Description: [paste key details — expected vs actual, repro steps]

Do not change any code yet.
1. Summarize what the issue is asking for.
2. Which files are most likely involved?
3. How do I run tests locally per CONTRIBUTING or README?

Sample implement prompt

Fix: https://github.com/owner/repo/issues/42
Summary: [one sentence from the issue]

Scope: minimal change in the files we identified. No refactors, no formatting sweeps, no new dependencies unless the issue requires it.
Done-when: [their test command from README] passes.
When to escalate to Plan Mode
If the fix needs schema + API + UI changes across unfamiliar modules, switch to Plan Mode — same workflow as Lesson 6, but the plan must respect CONTRIBUTING.md and existing patterns, not your personal project rule.

Do this now

One-session win — your first merged-quality PR attempt.

  1. Find an issue on a repo whose stack you know. Confirm no open PR already addresses it.
  2. Clone and install — run their test command before changing anything. Baseline must pass (or note pre-existing failures).
  3. Explore prompt — paste the sample above; read Agent's file list before implementing.
  4. Implement — Agent + @ on identified files only. Review the diff line by line.
  5. Verify + PR — their tests green; PR description includes the issue link (add Fixes #42 on its own line if you want GitHub to auto-close the issue on merge).

You are done when the PR is open and the diff contains only what the issue asked for.

Primary source: Cursor Quickstart — "Explain a codebase" is the explore step; attach context with @ once you know which files matter.
