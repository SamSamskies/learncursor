Lesson 11 · ~20 minutes

Cursor Hooks

Rules tell Agent what to prefer. Hooks run code when Agent acts — gate, log, format, follow up.

In Lesson 3 you wrote project rules — persistent prose Agent loads every session. In Lesson 10 you wired MCP — external tools Agent can call. Hooks sit on the agent loop itself: small scripts that fire at defined moments and can observe, block, or reshape behavior.

Rules are suggestions. Hooks are enforcement. When you need deterministic behavior — block a force push, log every shell command, format files after edits — hooks beat repeating it in prompts. Keep the Hooks reference open.

Rules vs MCP vs hooks

MechanismWhat it doesExample
Project rules Prose instructions Agent reads "Run npm test before marking done"
MCP External tools Agent invokes Playwright opens localhost:3000
Hooks Scripts on agent-loop events Deny git push --force to main

They stack. Your habit tracker might have a rule to run tests, Playwright MCP for browser verify, and a hook that blocks destructive git commands — each layer does what it's best at.

Four things hooks can do

BehaviorWhat happensTypical event
Observe Log or audit — no blocking afterShellExecution
Gate Allow, deny, or ask the user beforeShellExecution
Modify Rewrite tool input or inject context preToolUse, postToolUse
Follow up Send Agent another message stop, subagentStop

Two config locations

Project .cursor/hooks.json + .cursor/hooks/* — commit to git; paths relative to repo root
User ~/.cursor/hooks.json + ~/.cursor/hooks/* — personal hooks in every workspace

Same pattern as project rules vs user rules in Lesson 3, and project MCP vs global MCP in Lesson 10. Solo builders: start with one project hook on a repo you ship often.

Path gotcha
Project hooks run from the repo root — use .cursor/hooks/my-hook.sh. User hooks run from ~/.cursor/ — use ./hooks/my-hook.sh. Wrong path is the #1 reason a hook "does nothing."

How hooks communicate

Hooks are spawned processes. Cursor sends JSON on stdin; your script prints JSON on stdout. Exit code 0 = success; exit code 2 = block (same as returning deny). Official docs: Cursor — Hooks. 

// .cursor/hooks.json
{
  "version": 1,
  "hooks": {
    "beforeShellExecution": [
      {
        "command": ".cursor/hooks/block-force-push.sh",
        "matcher": "git push"
      }
    ]
  }
}

Each hook entry supports command (script), type: "prompt" (LLM evaluates policy), matcher (regex filter), timeout, and failClosed (block on crash/timeout). Matchers use JavaScript regex, not grep syntax.

Pick the narrowest event

You want to…Use this event
Block or approve shell commands beforeShellExecution
Log shell output after it runs afterShellExecution
Gate Playwright or other MCP calls beforeMCPExecution
Auto-format after Agent edits a file afterFileEdit
Intercept any tool call preToolUse / postToolUse
Scan prompts for secrets before send beforeSubmitPrompt

Prefer the specific event over the generic one. Gate shell commands with beforeShellExecution, not preToolUse, unless you need to rewrite the tool payload.

Starter hook: block force push

This gate hook matches your git safety instincts — Agent cannot force-push to main or master even if a prompt goes wrong. 

#!/bin/bash
# .cursor/hooks/block-force-push.sh
input=$(cat)
command=$(python3 -c "import sys,json; print(json.load(sys.stdin).get('command',''))")

if echo "$command" | grep -qE 'git push.*(-f|--force)'; then
  if echo "$command" | grep -qE '(main|master)'; then
    cat <<'EOF'
{"permission": "deny", "user_message": "Blocked: force push to main/master.", "agent_message": "Hook blocked force push to protected branch."}
EOF
    exit 0
  fi
fi

echo '{"permission": "allow"}'
exit 0

Gate hooks return permission: allow, deny, or ask (prompts you to approve). Make the script executable: chmod +x .cursor/hooks/block-force-push.sh.

Five-step setup loop

1. Choose event Pick the narrowest hook for your goal — see table above
2. Create hooks.json .cursor/hooks.json with version: 1 and one entry
3. Write script Read stdin JSON, print stdout JSON, chmod +x
4. Save Cursor reloads hooks.json on save; restart if needed
5. Trigger Ask Agent to run the gated action; check Settings → Hooks or Hooks output channel

Command vs prompt hooks

Command hooks (default) run a script — deterministic, auditable, best for gates and formatters. Prompt hooks send the hook input to an LLM with a natural-language policy — good for fuzzy "does this look safe?" checks when exact rules are hard to script. 

{
  "type": "prompt",
  "prompt": "Is this shell command read-only? Allow ls/cat/grep; deny rm/curl. Input: $ARGUMENTS",
  "timeout": 10
}

Prefer command hooks for anything security-critical. Use prompt hooks for lightweight policy when the logic is easier to describe than to code.

Start with one hook
Each hook adds latency and complexity. One well-tested gate beats a pile of hooks you forget to maintain. Add more only when Agent repeats a mistake rules can't fix.

Check your understanding

1. Share hooks via git with team.

2. Block a risky shell command.

3. Gate runs before shell executes.

Do this now

Install one project hook on a repo you actively build — habit tracker recommended.

  1. Pick a behavior — start with the force-push gate above, or an afterShellExecution audit log if you prefer observe-only first.
  2. Create .cursor/hooks.json — one event, one hook entry, optional matcher.
  3. Write the script in .cursor/hooks/ — read stdin, print JSON, chmod +x.
  4. Save and confirm — Settings → Hooks shows your hook; Hooks output channel logs when it fires.
  5. Test — ask Agent to run the gated action (e.g. run git push --force origin main) and confirm deny/allow behavior.
  6. Commit — hooks.json and scripts only (no secrets).

You are done when the hook fires on a real Agent action and you see it in the Hooks output channel.
